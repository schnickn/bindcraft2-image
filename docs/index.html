Design protein binders with BindCraft2 on Argon

You do not need to know BindCraft or Argon to use this. A small helper program called bc2 asks you a few questions, writes the files for you, and runs everything on the cluster. This page explains each step and lets you practice before you touch the real thing.

What is this?

Three ideas, in plain language.

BindCraft2

Software that designs new small proteins that stick to a protein you choose (the target). It uses AlphaFold 2 to imagine how a design would fold and bind, ProteinMPNN to refine the amino-acid sequence, then checks every candidate against strict quality filters. Designs that pass are called accepted.

Argon

The University of Iowa's shared research computer cluster. You log in from your own computer, but the heavy work runs on powerful machines with graphics cards (GPUs). You ask the cluster for a GPU and it runs your job when one is free.

bc2

A helper script that connects the two. It installs BindCraft2 for you, asks plain questions, writes the settings file, submits the job, and shows progress and results. You never edit a job script.

The one rule of the cluster: when you log in you land on a login node. It is only for typing commands and small tasks. Real work goes to the queue, and bc2 does that for you.

Words you will see

Skim this now and come back when a word is unfamiliar.

Target
The protein you want a binder for. You choose it.
Binder
The new protein BindCraft2 designs to stick to the target.
Hotspots
Residues (numbered amino acids) on the target that you want the binder to touch. Optional but helpful.
Campaign
One design project: one target, one binder type, one set of settings, one results folder.
Attempt (trajectory)
One try at designing a binder. Most attempts are rejected by the filters. That is normal.
Accepted design
A candidate that passed every filter. These are what you keep and test in the lab.
Login node
The machine you land on when you connect. For typing commands, not for heavy work.
Job / batch job
A task you hand to the cluster. It runs without you watching, even if you disconnect.
Queue
A waiting line for a kind of machine. Different queues have different rules (see Choosing a GPU).
GPU
A graphics card. BindCraft2 needs one. Types you will see: L40S, A40, A100, V100.
Worker
One design process. Several workers can share one GPU to design in parallel.
Container (.sif file)
A sealed box holding BindCraft2 and everything it needs, so nothing has to be installed by hand.

    Reading results

    When a campaign finishes (or any time during), bc2 results NAME lists the best accepted designs. Here is a real example from a test run, and what each column means.

    rankdesignlengthi_pTMi_pAEi_pDAEpLDDT
    1t-real_denovo_l75_76905d7f…_seq0750.850.150.470.93

    Example numbers from one real test design; a real campaign gives you a longer list.

    length
    Binder size in amino acids.
    i_pTM
    How confident AlphaFold is in the interface between binder and target. Higher is better (0 to 1). The standard filter wants at least 0.7.
    i_pAE
    Expected error at the interface. Lower is better. The standard filter wants 0.35 or less.
    pLDDT
    Confidence in the binder's own fold. Higher is better (0 to 1).
    i_pDAE
    The score the table is ranked by; lower is better.
    design
    The name of the design. The structure file with the same name ends in .cif.
    These thresholds are the defaults for the standard binder type, and other binder types can differ. A design that passed is a good candidate, not a proven binder. Testing in the lab is what confirms it.

    Where the files are

    Inside your campaign folder, ~/bc2/campaigns/NAME/results/:

    FolderWhat is in it
    3_Ranked/The accepted designs: structures (.cif) and the table !_Ranked.csv. Start here.
    1_Trajectories/Every attempt, including rejected ones, with a table of how each scored.
    2_Refolded/The sequence candidates that were re-checked with separate AlphaFold models.

    Getting them onto your computer

    bc2 results prints a ready-made scp command. Run it in a terminal on your own computer, not on Argon. Then open the .cif files in a free viewer such as UCSF ChimeraX, PyMOL, or the Mol* web viewer.

    Choosing a GPU

    The defaults are fine to start. This section explains the choice and lets you estimate memory for your own target.

    GPUMemoryTested with BindCraft2?Notes
    L40S48 GBYesRecommended. Common and fast.
    A4048 GBYesAlso good.
    A10080 GBYesFits the most workers or a bigger target, but UI-GPU often has a long wait for it. In a test it started in seconds on all.q.
    V10032 GBYesWorks, roughly 60% slower in a quick test.

    Queues

    QueueRule of thumb
    UI-GPUOpen to everyone. One running job at a time per person. Never interrupted. Default.
    all.qNo limit on jobs and often starts fast, but the cluster may interrupt your job at any time. Run bc2 run NAME again and it continues where it stopped.
    CCOM-GPUA group queue (L40S only). Only if you have access.

    Memory calculator

    Bigger complexes (target plus binder) need more GPU memory per worker. Enter your sizes:

    The estimate is the one BindCraft2 itself uses, from its source code. In our tests the real GPU use ran about 25 to 35 percent lower, so it errs on the safe side. It is a guide, not a guarantee. A very large target may not fit on a 48 GB card at all.

    First run is slower and heavier. The first time BindCraft2 runs on a given GPU type it compiles its code and saves the result in ~/bc2/xla_cache. In our tests that first run used about 29 GB of computer (host) memory with one worker, so keep the default request of 8 CPU slots (about 32 GB of RAM). Later runs on the same GPU type are faster and lighter.

    If something goes wrong

    Start with bc2 check (is the install complete?) and bc2 status NAME (what is it doing?).

    bc2: command not found

    Your shell does not know where the script is. Either start a fresh login session after adding it to your PATH (step 1), or run it by its full path: ~/bin/bc2 help.

    My job says “waiting” for a long time

    It is waiting for a free GPU. That is normal when the cluster is busy. See how busy a queue is with qstat -g c -q UI-GPU. Options: wait, pick a different GPU type with bc2 resources NAME, or try all.q (can be interrupted, but resumes).

    The job stopped before it finished

    On all.q the cluster can interrupt jobs; it can also happen if you cancel. Nothing is lost. Run bc2 run NAME again and the campaign continues from the last finished attempt.

    Status shows ERROR

    The scheduler could not start the job. Cancel it with bc2 cancel NAME, run bc2 run NAME --dry-run to see if the request is valid, and if the message is unclear send it to your instructor or Research Computing.

    I got a settings.json typo error

    Run bc2 edit NAME. It opens the file in nano and tells you when it is valid again. JSON needs commas between entries and double quotes around names. Save in nano with Ctrl-O then Enter, quit with Ctrl-X.

    Many attempts and still 0 accepted designs

    Hard targets can take many attempts, and that is normal. Check 1_Trajectories/!_Trajectories.csv to see why attempts fail. You can try a different length range, add hotspots to point the binder at a known site, or choose a different binder type. The attempts cap stops a run from going on forever.

    The job ran out of memory

    Lower the workers per GPU or switch to a GPU with more memory: bc2 resources NAME, then bc2 run NAME. Use the calculator above to see how many workers fit.

    bc2 setup failed to download

    If batch machines cannot reach the internet from your account, run it on the login node instead, inside screen so a dropped connection does not stop it: screen, then bc2 setup --here.

    Can I run it on the login node to test quickly?

    No. Use bc2 test for a tiny run through the queue. The login node is shared by everyone and has no GPU.

    Cheat sheet

    # once bc2 setup # download tools (batch job) bc2 check # is everything installed? bc2 test # tiny end-to-end test run # every project bc2 new # guided questions bc2 run NAME # submit (run again to resume) bc2 status [NAME] # progress bc2 results NAME # best designs + how to copy them bc2 cancel NAME # stop (progress is kept) # tweaks bc2 edit NAME # edit settings.json bc2 resources NAME # GPU type, queue, workers bc2 run NAME --dry-run # check the request first bc2 list # all campaigns

    What has been tested

    So you know how much to trust each part.

    Verified on Argon
    • A fresh bc2 setup as a batch job (about 8 minutes in our test; it can take longer when the cluster is busy).
    • The question-and-answer wizard with a built-in target and with a user's own PDB file, including wrong chain and hotspot answers being caught.
    • A real campaign submitted through the tool on an L40S, producing an accepted design.
    • Status while waiting and running, results, cancel, the duplicate-run check, the dry run, and bc2 test on a real install.
    • Pausing and resuming: cancelling a campaign part-way, then running it again, carried on with the next attempt, kept the earlier results, and finished with an accepted design.
    • bc2 edit (including catching a deliberate typo) and bc2 resources.
    • BindCraft2 1.0.4 on L40S GPUs: 1, 2 and 3 workers sharing one GPU, and a single job on 4 GPUs with 2 workers each (8 workers), including one submitted through bc2 new with the new GPU-count question.
    • Nanobody (VHH) campaigns with 1 and 2 workers, and short runs of scFv, Fab and ARP binders. Each ran through the whole design pipeline; none was long enough to judge design quality.
    • Earlier BindCraft2 1.0.3 on A40, A100 and V100 GPUs.
    Not tested yet
    • Targets given as mmCIF or FASTA files, and targets with several chains.
    • A40, A100 and V100 GPUs with BindCraft2 1.0.4 (they worked with 1.0.3).
    • More than one GPU on A40 (accepted by the scheduler but not run), and on A100 or V100 (the scheduler refuses; they usually allow 1).
    • Long, real campaigns with many designs, and a first-time user on a different account.

    The output you see in the walkthrough is based on real runs, with names and numbers simplified.
